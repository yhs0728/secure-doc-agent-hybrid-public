# 백엔드 MVP 검증 설계

## 검증 원칙

테스트를 세 층으로 나눕니다.

1. 단위 테스트는 문서 로딩, 청킹, manifest 비교, 오류 변환처럼 실패 원인을 좁혀야 하는 규칙을 검증합니다.
2. 통합 테스트는 실제 FAISS 파일과 API 계약을 사용하되 임베딩/LLM은 결정적인 테스트 대역을 사용합니다.
3. 실제 E2E는 업로드 API부터 실제 MiniLM, 디스크 FAISS, Ollama `qwen3:4b-instruct`, 답변/인용까지 운영 경로를 그대로 통과합니다.

실제 모델 테스트만 두면 느리고 비결정적이며, 가짜 모델 테스트만 두면 모델·드라이버·파일 포맷 통합 실패를 놓칩니다. 세 층의 목적을 분리하는 것이 중요합니다.

## 실제 모델 E2E 시나리오

| 시나리오 | 핵심 검증 | 합격 기준 |
|---|---|---|
| TXT 업로드 후 질문 | 업로드, UTF-8 로딩, 임베딩, 생성 | 200, 고유 값이 답변에 있고 TXT가 인용됨 |
| PDF 업로드 후 질문 | PDF 파서와 영문 임베딩 | 200, PDF가 인용됨 |
| DOCX 업로드 후 질문 | DOCX 파서와 한국어 검색 | 200, DOCX가 인용됨 |
| 관련 문서 없음 | 과잉 답변/과잉 인용 방지 | 빈 인용, `requires_human_review=true` |
| 삭제 후 동일 질문 | 원본 삭제와 청크 삭제의 일관성 | 삭제한 파일이 인용되지 않고 답변 차단 |
| 재시작 후 동일 질문 | 영속 인덱스 재사용 | 검색 성공, `index.faiss` 수정 시각 불변 |
| Ollama 종료 | 연결 오류 분류 | 503, `LLM_UNAVAILABLE`, request ID 존재 |
| 응답 시간 초과 | timeout 분류 | 504, `LLM_TIMEOUT`, request ID 존재 |

연결 종료 시나리오는 실제 Ollama 프로세스를 강제로 종료하지 않고 연결될 수 없는 로컬 포트를 사용합니다. 이렇게 해야 개발자의 다른 작업을 방해하지 않으면서 동일한 클라이언트 오류 경로를 결정적으로 검증할 수 있습니다.

## 검색 품질 평가 설계

평가 문항은 파일 형식이 아니라 의미적 검색 난이도를 기준으로 구성했습니다.

- 정책의 숫자·주기: 90일, 5회, 30분, 02:00
- 조건·주체: 관리자 확인, 담당자 승인, 부서장 승인
- 비슷한 주제의 구분: 일반 보안 정책과 원격 접속 정책
- 중복 또는 대체 정답: 같은 백업 내용을 담은 두 PDF처럼 둘 중 하나가 정답인 경우
- 부정 문항: 식당, 연봉, 주차처럼 문서 집합에 근거가 없는 질문

`expected_sources`는 허용 가능한 정답 문서 집합입니다. Top-1/Top-3은 그 집합 중 하나가 검색되면 성공입니다. 최종 인용은 최소 하나의 정답을 포함해야 하며, 인용된 모든 파일이 허용 집합 안에 있어야 “관련 없는 인용 없음”으로 집계합니다. 부정 문항은 빈 인용과 사람 검토 플래그가 동시에 있어야 성공입니다.

권장 MVP 기준은 Top-1 80% 이상, Top-3 95% 이상, 정답 인용 90% 이상, 무관 인용 방지 95% 이상, 근거 없는 답변 차단 100%입니다. 이 수치는 초기 운영 기준이며 문서가 늘면 재측정해 조정합니다. KURE-v1 전환은 동일 데이터로 반복 실행해 MiniLM 대비 유의미한 개선이 있고 지연 시간과 메모리 증가를 감당할 수 있을 때 결정합니다.

### 2026-10-07 실측 결과

| 지표 | 결과 |
|---|---:|
| Top-1 정확도 | 78.9% (15/19) |
| Top-3 정확도 | 94.7% (18/19) |
| 정답 인용 포함 | 94.7% (18/19) |
| 무관 인용 방지 | 100% (22/22) |
| 근거 없는 답변 차단 | 100% (3/3) |

Top-3 및 정답 인용 실패는 “보안 사고를 발견하면 누구에게 신고해야 하나요?” 한 문항입니다. 정답 문서가 검색 후보에 없었고 생성기는 이를 꾸며내지 않고 빈 인용으로 차단했습니다. 안전성 기준은 충족하지만 검색 재현율 기준에는 한 문항이 부족합니다. 따라서 현재 MiniLM을 즉시 제거하기보다는 이 결과를 기준선으로 고정하고, KURE-v1을 동일 22문항으로 평가해 Top-3/인용 개선 폭과 지연 시간·메모리를 비교한 뒤 교체하는 것이 타당합니다.

## 인덱스 복구와 재시작

정상 재시작 테스트에서는 첫 빌드 후 두 번째 `build_or_update_index` 호출의 문서 임베딩 횟수가 증가하지 않는지 확인하고 실제 유사도 검색까지 수행합니다. 다음 고장은 모두 전체 재구축이 정답입니다.

- `index.faiss` 손상: FAISS 로드 실패 후 재구축
- `index.pkl` 누락: 완전한 스냅샷이 아니므로 재구축
- manifest JSON 손상: 구성을 신뢰할 수 없으므로 재구축
- 임베딩 모델명 변경: 벡터 공간이 다르므로 재구축
- 청크 크기/overlap 변경: 문서와 chunk ID 경계가 달라지므로 재구축

스냅샷은 `temporary`에 세 파일을 모두 쓴 후 `current`로 디렉터리 단위 교체합니다. 직전 `current`는 `backup`으로 이동합니다. manifest와 FAISS의 chunk ID 집합도 커밋 전에 비교합니다.

## 동시성 정책

질문은 Retriever 객체를 지역 참조로 잡고 실행하므로 갱신 도중에도 기존 스냅샷을 안전하게 읽습니다. 모든 쓰기 경로는 같은 재진입 락을 사용합니다. 새 스냅샷 커밋 후 그래프 캐시를 비우며, 그 이후 시작한 질문은 새 인덱스로 그래프를 구성합니다.

이 보장은 `--workers 1`인 단일 프로세스 범위입니다. 여러 worker나 여러 서버로 확장할 때는 파일 락/분산 락과 명시적인 버전 기반 Retriever 교체가 추가로 필요합니다.

## API 계약에서 중요한 점

성공 응답은 프런트엔드가 바로 렌더링할 수 있도록 `answer`, `citations`, `requires_human_review` 세 필드를 유지합니다. 오류는 상태 코드별로 JSON 구조가 달라지지 않도록 `error.code`, `error.message`, `error.request_id`로 통일합니다. 사람에게 보여줄 문구와 프런트 분기에 사용할 안정적인 코드를 분리했으며, 로그 추적용 request ID를 헤더와 본문에 함께 제공합니다.
